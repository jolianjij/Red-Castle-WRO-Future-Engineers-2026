03The five commands

Almost everything is one of these.

./sync.sh pull          # Pi -> laptop. Do this BEFORE editing.
./sync.sh push-safe     # laptop -> Pi, only if the tests pass
./backup.sh save "it worked"
./backup.sh undo        # undo the last push or restore
ssh pi@raspberrypi
Pull before you edit. You tune values directly on the Pi between runs. push overwrites them — that is what push means. If it has already happened, ./backup.sh undo.

04Before every run

python tools/test_logic.py   # 146 assertions, laptop, no Pi needed
python tools/dryrun.py       # live camera, motor never touched
Compiling is not testing. A build once shipped with a NameError on a live code path because it had only been checked with py_compile. Every bug found in this project has a test pinning it, so none of them can come back quietly.

Windows cannot see the Ethernet hardware at all. The Realtek PCIe GbE Family Controller reports Present: False, error code 45 — “not connected to the computer”. That is not a driver problem: a missing driver still shows the device with a warning. It means the controller is switched off below the operating system, so no cable and no setting on the Pi can help until it comes back.
  1. A true cold boot. Windows Fast Startup means “Shut down” restores a saved state, so a device that failed to appear stays missing across many shutdowns. Hold Shift while clicking Shut down — or simply Restart, which does do a full boot.
  2. UEFI. Tap F2 at the Lenovo splash. Look under Configuration for LAN / Onboard LAN / Ethernet. If you cannot find it, Load Setup Defaults (F9) then Save & Exit re-enables a disabled LAN without hunting.
  3. Rescan, from an Administrator terminal: pnputil /scan-devices
  4. A USB-to-Ethernet adapter. About $10, any RTL8153 or AX88179 based one — Windows 11 has the drivers built in, and the Pi needs no changes at all. Buy one regardless of how the checks above go: this single link is the only path to the robot at a venue that bans wireless, and there is currently no spare.

Once any of those gives you a wired adapter, there is nothing to configure — leave it on automatic DHCP, plug in, wait about ten seconds:

ssh pi@192.168.50.1            # proves the CABLE specifically
./tools/venue_net.sh status    # must say the laptop is ANSWERING
./tools/venue_net.sh wifi-off  # only then
Use the address, not the name, to test the cable. With Wi-Fi and the cable both up, the Pi advertises both of its addresses over mDNS, so raspberrypi.local may quietly resolve to the Wi-Fi one and you will not have tested the cable at all.
The guard will protect you. wifi-off refuses unless the laptop has actually taken an address from the Pi and answers a ping. A carrier alone is not enough — a router or an idle port raises one too, and that exact mistake once left the robot unreachable.
